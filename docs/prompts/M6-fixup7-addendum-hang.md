## Facts: GitHub Actions run of commit 05e719b (Qt 6.8.2)

- **Ubuntu: 34 of 34 pass** (`100% tests passed out of 34`), including `tst_HiDpi` (1.56 s). So the Application dialog fix works on Linux CI.
- **Windows: the job hangs.** ctest timeline from the log: `00:06:10 Start 34: tst_HiDpi`; `00:07:14 33/34 tst_EmptyStatesAndFocus Passed`; then nothing; `00:40:39 ##[error]The operation was canceled.` (the job reached its time limit, about 45 minutes in total). 33 tests passed, `tst_HiDpi` is the only one that never finished, after more than 33 minutes. The "Diagnose failed tests", "Registry write probe" and "Upload test logs" steps were cancelled, so **there are no logs of the hang at all**.
- Previous Windows run (commit 32a6f29): `tst_HiDpi` finished in 14.5 s (and failed on the dialog scroll buttons). So the hang is new and was introduced by the commits between `32a6f29` and `05e719b`.
- Other Windows timings in this run (debug build, MSVC): `tst_PageStudy` 138 s, `tst_PageHome` 124 s, `tst_PageJobs` 86 s, `tst_EmptyStatesAndFocus` 66 s.

## Tasks

1. **Workflow hygiene (commit 1).** A hang must fail one test and keep the logs, not kill the job. In `.github/workflows/ci.yml`:
   a. Run ctest with a per-test timeout: for example `--timeout 600` on the Windows and Linux ctest calls (the slowest test takes 140 s on Windows, so 600 s is generous; Linux unchanged otherwise). If you prefer it in CMake (`set_tests_properties(... PROPERTIES TIMEOUT 600)` for the `ui` label), say which and why; one place only.
   b. Put `timeout-minutes` on the "Run quality gate" steps (Windows 30, Linux 15, adjust if you can justify other numbers) so that a stuck step **fails** instead of the whole job being cancelled; the following `if: failure()` steps (diagnose, registry probe, artifact upload) then still run.
   c. Make sure the Windows ctest call prints the captured output of a timed-out test (`--output-on-failure`, which is already there for failures; show with a `git diff` that nothing else changed).
   d. YAML parse and `git diff`. Do not change anything else in the workflow.

2. **Find the cause in the code first.** `git diff 32a6f29..05e719b --stat` and `git diff 32a6f29..05e719b -- tests/ui/tst_HiDpi.cpp src/ui` (raw). Look for anything that can wait or loop without a bound and that behaves differently on Windows/MSVC or on the `offscreen` platform there: `while` loops with `processEvents()`, `QTRY_*`, `QTest::qWait`, `qWaitForWindowExposed`, `QEventLoop`, `dialog.exec()` or any modal call in a test, `show()` of a dialog that opens a message box, resize/min-size feedback (a `resizeEvent`, `showEvent` or `changeEvent` that calls `setMinimumSize`, `resize` or `adjustSize` and so triggers another layout pass without end), and loops over fonts, dialogs, sizes and themes that multiply a slow Windows debug operation. List each candidate with the file and line from a command (`grep -n`), not from memory. Say which one you think it is and why; label it as a hypothesis.

3. **Instrument `tst_HiDpi` so that the next Windows run tells us exactly where it stops (commit 2).** Test-only, all lines `// CI-DIAG`:
   a. Before every step of every slot (page, theme, size; dialog, theme, size, tab) print a progress line with `qInfo()` and flush (`fflush(stderr)` if needed), for example `CI-DIAG progress: testDialogsHiDpi dialog=ApplicationDialog theme=Dark size=sizeHint tab=2 t=<elapsed ms>`.
   b. A watchdog: a `std::thread` started in `initTestCase` that, after 240 s without a progress update, prints the last progress line and `QStandardPaths`-free state (thread id, `QThread::currentThread()` of the GUI thread is not needed) and calls `std::_Exit(3)`; the progress variable is a `std::atomic`/mutex-guarded string. It must be disarmed in `cleanupTestCase`. This guarantees a visible last-progress line even if the main thread is stuck in an event loop or a layout storm. Test-only; document it in a comment; no effect on other tests.
   c. Run the binary locally under the same conditions as CI as far as you can (`QT_QPA_PLATFORM=offscreen QT_SCALE_FACTOR=1.5`, fonts `DejaVu Sans` and `Liberation Sans`, and with the Qt 6.8.2 build from fix-up 7 if you have it); paste the progress output and total time (raw). If a loop or a very slow step is visible locally (for example thousands of progress lines, or one dialog taking seconds), report the numbers; that is probably the hang.

4. **Fix (commit 3), only if the cause is evidenced.** If a feedback loop, an unbounded wait or a modal call is found, fix it at the source (the dialog/layout code or the test), not by raising timeouts. If it is not found, do not guess a fix: keep the instrumentation and the workflow hygiene, say plainly "cause not found, next Windows run will show the last progress line", and do not claim anything about Windows.

5. **Report section.** Facts as given; evidence for tasks 1 to 4; an honest prediction (label it as such) for the next Windows run (finishes / fails with a visible last progress line / still unknown); "Not verified by agent, user to check": the Windows result (user pushes and reads the run; if the job times out again the per-test timeout and the step timeout must have produced logs and an artifact, check that). End with `CMAKE_BUILD_PARALLEL_LEVEL=2 ./scripts/check.sh` full raw output, totals by command (binaries and `-functions` lines by the counter command), `git status --short`, `git log --oneline` of this task. `m6` is not ready to tag.

## What I found in the three reports

1. **The real-data evidence contradicts itself (D2 fix-ups §2).** §2.1: `ls -l` shows `jobprep.sqlite` modified `Nov 3 02:20`, size 49152, and the newest `reminders_sent` row is `('overdue:2:2026-11-03', '2026-11-03T02:20:12')`. §2.3: `stat` of the same file shows `2026-10-31 12:25:57`, before **and** after the isolated run. A file that contains a row written on Nov 3 02:20:12 cannot have an mtime of Oct 31 (unless it was replaced, or SQLite is in WAL mode and the main file was not checkpointed, but then `-wal`/`-shm` files should have been listed). The "isolation proof" compares two `stat` lines that are both already inconsistent with §2.1, so it proves nothing yet. Also `backups/` has mtime `Nov 3 15:43` and nobody looked inside.
2. **An isolated full test run still writes outside the temp dirs.** CI fix-up 5 §4d: after `HOME=/tmp/jp-home-ci5 XDG_DATA_HOME=... ctest`, `find` printed `/tmp/jp-home-ci5/.local/share/JobPrepTest/JobPrepTest_7614/backups/pre-restore-20261104-134407.json`. The report blames `tst_ImportExport::testRestoreSafetyBackupProductionPathWithCustomXdgDataHome`, "as designed". That cannot be right: that slot sets `XDG_DATA_HOME` to its own `QTemporaryDir` and asserts that the path starts with it, so its file would be under that temp dir, not under the fake home. The names `JobPrepTest` / `JobPrepTest_<pid>` look like `TestSettingsScope` (organization/application name). So some test (probably one that now uses `TestSettingsScope` and runs a restore with the default safety directory) writes a safety backup into the real AppData location. On the developer's machine that is `~/.local/share/JobPrepTest/...`; on Windows `%LOCALAPPDATA%\JobPrepTest\...`. It does not touch production data, but it breaks our own rule ("tests never touch real user locations").

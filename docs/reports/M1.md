### Bugs fixed in this milestone

1. **`QSqlQuery::bindValue()` segfaults in the SQLite driver (blocked 7 of 9 tests).**
   The crash occurred inside `libqsqlite` during `SqlStatement::exec()`. It was reproduced with roughly 40 lines of stock Qt and no JobPrep code: `addBindValue()` succeeds in the same program where `bindValue()` crashes for `QString`, for `QVariant`, and with an explicit `QSql::In`. All Qt packages report the same version, so this is a defect in that Qt build rather than an ABI mismatch.
   `SqlStatement` therefore binds with `addBindValue()`. Because that is positional, `bind()` enforces that indices run `1..N` in placeholder order; an out-of-order index is reported through `Database::lastError()` and makes `exec()` fail rather than silently filling the wrong column. Qt drops bound values after each successful `exec()`, so a statement reused in a loop (`updatePositions`, `reorderSubtasks`) rebinds from the first placeholder.
2. **Null `QString` was stored as SQL `NULL`.** A default-constructed `QString` is a null `QVariant`, which the SQLite driver binds as `NULL`, so `NOT NULL` columns rejected the row (`tracks.icon`, `topics.notes`). Now stored as empty text, matching the schema's `DEFAULT ''`.
3. **Invalid SQL: `ORDER BY … WHERE …`.** `TopicRepository::subtasks` and `ApplicationRepository::statusHistory` appended `WHERE` to a helper that already contained `ORDER BY`. The `ORDER BY` clause moved into its own helper appended after the caller's `WHERE`.
4. **`ApplicationRepository::updateRow` re-bound placeholder 12** after binding `1..17`, relying on true positional binding. Rule A5 now lives in `bindApplication`, so every path applies it identically.
5. **First-pass compile/link defects:** `SessionRepository` referenced an undefined `kSelectAll`; `Database`'s default connection argument was not header-safe; `TrackRepository.cpp` missed `<QSqlError>`; `Q_INIT_RESOURCE(resources)` needed external linkage; `MessageCapture.cpp` used `m_messages` instead of `s_messages`; missing includes in `TestDatabase.cpp`, `main.cpp`, `tst_UiSmoke.cpp`.
6. **Three test assertions were wrong, not the code** (the implementation was correct in each case):
   - `duplicateCopiesFieldsWithOwnHistory` compared the copy against a local struct mutated after it was read from the database, so `duplicate()` correctly copied the stored (empty) `notes`. The notes are now persisted first.
   - `removeKeepsSessionsButClearsTopic` expected `SessionRepository::count() == 0` while its own next line asserts the session survives with a NULL `topic_id` (`study_sessions.topic_id` is `ON DELETE SET NULL`). Expected value corrected to `1`.
   - `reorderSubtasksRewritesOrder` reused one `QSignalSpy` across `addTopic` and `addSubtask`, which also emit `changed()`. A dedicated spy now asserts the failed reorder emits nothing.

## Deviations and assumptions

1. **Binding API deviates from the plan.** `SqlStatement` uses `addBindValue()` with mandatory in-order binding instead of `bindValue(index, …)`, because `bindValue()` segfaults in this Qt's SQLite driver. This is portable to Qt 6.5+ and to every driver, but it is a stricter contract for every future repository.
2. **`Database::Transaction` supports nesting** (via savepoints), though the plan specified no nesting. Seeding wraps repository writes in one outer transaction for atomicity, which requires it.
3. **Files added beyond the plan's list:** `src/data/SqlStatement.*` (explicitly permitted), `src/data/DataLogging.h`, and the test helpers `tests/data/MessageCapture.*`. `MessageCapture` exists so tests can assert that expected "no row" failures are quiet while real SQL errors stay loud.
4. **First-launch "No" is final** for v1; there is no Settings-page opt-out yet, as the Settings page arrives in M6.
5. **Rule A5 and the initial `status_history` row live in `ApplicationRepository`**, because no application service exists yet. They should move to a service layer in M2 once models and services land.
6. **`nextUpcoming` filters past and cancelled sessions** but does not filter other statuses; the pre-existing test name `nextUpcomingSkipsPastAndCancelled` overstated this and was renamed to `nextUpcomingSkipsPast`. Flagging it so it can be revisited when the agenda is built in M3.
7. **Windows was not built or run.** Nothing OS-specific was added, so no Windows-only code is expected, but MSVC has not verified this milestone.
8. **`docs/SPEC.md` §14** received exactly the two entries the plan allows (`sampleDataPrompted` setting; `insert()` writes an initial `status_history` row). No other part of the spec was touched.
